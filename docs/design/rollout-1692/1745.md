## Decisive timezone diagnosis and fixes

Used diagnosing-bugs and TDD at the approved assembled component/route/domain seams. The first command was `pnpm --filter webapp exec vitest run --project unit src/components/time-tracking/time-clock-popover.transport.test.tsx -t 'asks before'`. It failed because the real header -> query hook -> command transport did not display the confirmation. The test keeps production query/transport/capture/choice implementations; it does not replace the clock hook with a mocked command callback. Browser and saved-zone boundaries are explicit.

Before further probes, ranked falsifiable hypotheses were: missing header confirmation; original saved-preference setup absent; transport performing confirmation later; stale browser/query context. The [controlled before observation](1745/before-timezone.json) proves the first. A real synthetic manager's PERSONAL setting was explicitly written through the timezone UI and read from `user_settings` through the scoped employee/user relationship. With saved **Europe/Berlin**, browser `Intl` reported **America/New_York**. Full-widget Cancel sent no clock command. Header clock-out sent immediately without confirmation. The endpoint persisted New York and server-derived **-300** minutes; transport did not prevent submission. The #1700 uncontrolled probe alone was insufficient evidence, but the controlled loop establishes a product gap.

`useHeaderClockTimezone` adds only UI confirmation around the header's existing submissions. It reuses the existing dialog and personal preference action, retains the click's booking choices, sends the confirmed browser zone, and bypasses the deferred dialog for existing offline event capture. It makes no preference write or clock command before confirmation. Pending actions prevent duplicate continuation/dismissal. Confirmation is bound to the existing user, active organization, employee and displayed work; changing that scope or unmounting the header during preference saving prevents the clock continuation. A requested personal save can finish independently; no automatic rollback or new transaction boundary was added.

The real nested dialog initially dismissed the parent popover, hiding post-clock-out notes. An assembled notes-visibility regression went red. The parent now ignores close requests from its confirmation portal while that prompt owns focus; booking and notes retain their existing mounted state.

The runtime also reproduced a streamed header hydration mismatch: SSR emitted a loading button, but another clock consumer had already populated the shared query before header hydration. A render-to-string/hydrate test with that real query cache went red. A stable `useSyncExternalStore` hydration snapshot now keeps the initial markup consistent, then reads the same shared clock query. No second clock query/timer/controller was added.

[After evidence](1745/after-timezone.json), [before capture](1745/before-header.png), [after capture](1745/after-header.png), and [held pending request](1745/timezone-pending.png) record the actual outcomes:

- Full widget and header both prompt on the **same active work** with saved Berlin/browser New York.
- Cancel sends nothing and leaves Berlin saved. Continue once uses New York and leaves Berlin saved.
- Update timezone and continue persists New York before clocking in; the next matching-zone clock-out needs no prompt. The fixture's saved zone was restored through its real UI afterward.
- An intercepted actual clock POST was held, not replaced with a fabricated response. All continuation/cancel buttons were disabled; only one request existed before release to the actual server.
- Linked `time_entry` and `work_period` rows retain canonical UTC instants and independently captured +60/-300 offsets with `timezone_source=browser`. `persistedPeriods` records canonical elapsed seconds and the existing rounded minute value. Short synthetic work can legitimately total zero minutes; no formula changed.

Before/after share the fixture, actor and application scope. They are distinct clock observations with additional short real records after the baseline, not identical historical datasets. Preliminary driver-created records were preserved and completed through the actual UI. No queued/uncertain records were deleted to manufacture success.
