## Implementation

The existing F1 AuthFormWrapper now receives the real domain branding in review, loading and success states. A divided definition list places workspace, invited email, role and inviter before the action without nested fact cards. One task h1 remains. Shared auth controls/legal links, logo behavior, background, saved preferences and locale navigation remain owned by the existing shell. Labels and buttons wrap at large text sizes. This purpose-built authentication review remains a full bounded flow rather than a CRUD panel; it has no editable fields or legacy react-hook-form form to migrate.

Temporary acceptance errors no longer imply that the invitation itself is permanently unavailable: the context, error and retry action stay present. Account switching has guarded pending/error/retry feedback and still uses the one native-aware signOut owner, clears manual-entry recovery on success and preserves its callback. Buttons have explicit `type="button"` to avoid the wrapper's native POST default. Existing Alert/status/Button primitives provide announced failure/progress and focus; spinners honor reduced motion. Success still uses the original 800ms `/init` handoff. No endpoint, server action, schema, permission reader, joining owner, Temporal comparison or callback transport changed.

Security review: the server page's existing token lookup and minimal payload remain byte-identical; the client sends only `invitationId` for acceptance. Better Auth and its coordinated organization-scoped transaction still decide recipient/status/expiry, membership and joining/reactivation. React escapes all invitation context. No new HTML injection, secret logging, session minting or auth guard bypass. Real wrong-account acceptance returned 403; stale revocation was refused. The recipient began with the **large** organization active and joined **small** via the invitation target, without borrowing its existing membership's authority. There is no organization switcher in this shell. Joining/transaction integration regressions cover current/deactivated/departed variants; the UI does not infer lifecycle outcomes from the membership role.
