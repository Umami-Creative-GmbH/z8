## Final capability comparison and lifetime

Every capability in the inventory remains mapped to the refreshed page. The single semantic welcome heading and shared progress lead one bounded opaque surface. The original three capability descriptions remain in divided rows. The actual summary supplies organization-arrival text and the existing Continue Setup/Get Started choice; the only continuation destinations remain profile and organization. All shell theme/font/language/legal controls and real background selection remain owned by the unchanged shell. There are no editable fields, form conversions, new dates, permissions, features, shortcuts or server actions.

`WelcomePageClient` observes the existing session hook; it does not resolve or fabricate authority. Its account/active-organization key remounts only the page-local arrival on scope changes, including A→B→A. Each preparation effect has its own active token; cleanup on unmount/hidden Activity invalidates all late state/error/navigation consequences. Deferred effect dispatch avoids a duplicate initialization during StrictMode replay. Successful initialization is remembered within that arrival so a summary retry does not repeat the mutation. Reappearing cached Activity obtains a fresh summary before continuation. A refused/rejected initialization can retry; a refused/rejected summary never becomes a false no-organization result.

Continuation has explicit idle/pending/continuing/failed states and an immediate per-arrival duplicate guard. A successful server step update keeps the action locked while routing. Refusal/transport rejection returns the same action with an inline recoverable error. Unknown transport diagnostics are not exposed. Obsolete success/refusal/rejection cannot change the current page or navigate. Already dispatched server writes are not cancelled by a client lifecycle guard; unchanged request authentication and domain ownership remain authoritative. This is UI lifetime protection, not new membership admission or a guarantee that a server write was rolled back.

The server page/actions, OnboardingService, `/init`, joining, auth/session owners, membership/security checks, shared onboarding shell/progress/run-action, generated auth/catalog files and unrelated payroll/heading files are unchanged. The userSettings initialization timestamp/step and actual membership reads retain their existing owners and representations.
