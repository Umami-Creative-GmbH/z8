# Webapp shared UI pattern inventory

Status: factual discovery for draft issue #1692, 14 November 2026. Recommendations and unresolved product questions below are proposals, not approved implementation decisions. No application code changed for this inventory.

This inventory covers reusable presentation and interaction patterns used by user-facing `apps/webapp` route templates, including authentication, setup, public/shared, ordinary app, settings and platform administration. It samples representative consumers; it is not a capability inventory for every route or a live accessibility audit. A route's implementation ticket must still trace every action, state, permission and preference before changing it.

Read the [UI and UX language](../refs/ux-language.md), [approved screen brief](2026-11-14-dashboard-time-tracking-redesign.md), [design context](../refs/design-context.md), [project conventions](../refs/project-conventions.md) and [agent workflow](../refs/agent-workflow.md) alongside this evidence. The prototype's omissions do not authorize deleting capabilities. The current repository already contains dashboard/time-tracking refresh components; this inventory describes the files inspected, without treating their presence as proof of runtime completion.

## High-risk contracts for route capability inventories

1. **Multiple clock presentations must share one truth.** Global popover, dashboard personal day, time tracking, calendar live entries and offline state must agree. Project/task requirements, billability, vehicle use, workplace policy and timezone mismatch continuation all appear in current clock/manual workflows. Keep their state/action owners behind any refreshed action band.
2. **Manual entry is a transaction/recovery workflow.** `time-tracking/manual-time-entry-dialog.tsx` includes target employee context, repeated wall-time occurrence choices, timezone update/continue-once/cancel, vehicle warnings and frozen-command recovery. Its lookup distinguishes committed, not committed, conflict, unsupported and refused. Treat these as capabilities, not excess form complexity.
3. **Dates and amounts are not presentation-only values.** [Timekeeping](../refs/timekeeping.md) defines UTC durations, endpoint offsets and employee-calendar grouping. Calendar selection and scheduling shift dates have different zone owners. Preserve authoritative totals/precision and unknown values; do not recompute from displayed strings or equate unavailable with zero.
4. **A uniform record row must retain its domain action model.** Inbox eligibility, delegated approvals, rejection reasons, corrections, archived/historical entities, document access, payroll readiness and irreversible employee lifecycle work need their existing guards and outcomes. Existing role/feature checks in a component are not authorization replacements.
5. **Export/share/download are distinct workflows.** Employee exports, payroll runs, audit packages, frozen report share links and one-run external download links expose different data and lifecycles. `reports/projects/shared-report-view.tsx` uses the same frozen snapshot document for its view and downloads; share creation shows a secret URL once. Preserve redaction, expiry, one-time reveal and exact viewed/exported scope.
6. **Refreshing does not start the page over.** Preserve `ViewRefreshProvider` registrations and snapshot ownership, and do not remount forms to indicate loading. Keep stale data and draft input visible when their current owners support it.
7. **Planning has consequences beyond positioning a block.** Scheduling publishes with `use-shift-publish-flow.ts` and an evaluation fingerprint; acknowledgement must remain tied to the evaluated warnings. Keep skill overrides, request decisions, coverage context and a usable phone task path alongside calendar gestures.
8. **Settings visibility and access are different layers.** Navigation still consumes `SettingsAccessTier` while settings actions use the four-level organization-action model. Follow [ADR 0002](../adr/0002-settings-actions-authorize-by-settings-access-not-casl.md); preserve required levels and object checks. A presentation ticket cannot harmonize these enums or broaden access.
9. **The web UI also runs in a store shell.** [ADR 0001](../adr/0001-store-apps-are-a-thin-shell-around-the-web-app.md) makes web safe areas, phone navigation, system-browser sign-in handoff and offline clocking part of the webapp contract even though other applications are outside this spec's route scope.
10. **Heading ownership changes require coordination.** `SiteHeader` supplies an `h1` on routes other than dashboard/time tracking; calendar page/view has no own `h1`, while reports and approvals do. Replacing the shell heading everywhere before adding route headings creates missing titles; adding route headings everywhere first creates duplicates. The shared owner must record shell-owned versus page-owned `h1` per route and stage adoption. `route-metadata.ts` resolves by longest matching path prefix and has a generic Z8 fallback; it is a title registry, not proof of complete route coverage.

Shared changes may proceed in parallel only after ownership and interfaces are explicit.

## Concrete product decisions still needed

The approved UX language establishes restraint, preservation and accessibility. It does not resolve every choice below. The implementation specification should make each choice explicitly or assign its decision to a named shared owner before dependent tickets start.

| Decision | What current code leaves open | Required resolution/evidence |
| --- | --- | --- |
| Title ownership and density | Shell route title and local page headings coexist; settings/card/public variants differ. | Decide when header is location context versus the page's single title, title/action sizing and whether genuinely wide workspaces have a separate width/density treatment. Preserve semantic heading structure. |
| Phone record strategy — approved | Some consumers stack all cells; others scroll or pin actions. | The user approved task-specific adaptation: ordinary lists prioritize identity/status/actions with accessible detail; comparison-heavy reports and planners may scroll locally. Require a field/action mapping; every field and action remains available. |
| Selection meaning | Tables, paged lists and inbox decide selection differently. | State current page/loaded results/all matching where relevant, what filter/page changes do, and how partial/unauthorized bulk outcomes are reported. Preserve existing semantics unless separately approved. |

| Error/empty/restricted copy | Multiple honest domain distinctions have different presentation. | Decide reusable state families and how inline, region, page and global failures relate. | Calendar/planning common ground | Record calendars, planning calendars and phone agendas serve different jobs. | Decide common control styling and responsive behavior while keeping event types, zones, selected scope and action models distinct. | Shared export action placement | Reports, payroll, scheduled exports and audit data use separate commands. | Decide consistent placement/feedback while retaining domain-specific formats, preview scope, readiness and lifecycle. Do not add a universal export that silently changes dataset scope. |

Audit metadata against the route inventory, rather than deriving scope from metadata. |

The most useful next design choices are about interaction preferences, not facts the repository can answer:

- **Dense records on phones:** recommend task-specific adaptation: stacked identity/details for ordinary CRUD lists, scrolling with reachable actions for cross-column comparison, and an agenda for a time-based personal schedule. This preserves detail and a practical task path; a mandatory single phone layout would be visually more uniform but would make some comparisons or long forms harder. Define the choice per route under one shared table contract.
- **CRUD consistency:** recommend consistent field/validation/save/cancel language and shared ActionPanel layout for ordinary create/edit tasks, while short destructive confirmations, long multistep configuration and operational recovery retain a container suited to their consequence. The tradeoff is a small, documented family of containers instead of moving every task to the same modal or route. Do not standardize away reasons, draft lifetime or required acknowledgment.
- **Labels and route identity:** recommend consistent user-facing domain terms in navigation, headings and feedback while keeping current route URLs and redirect contracts during visual adoption. This reduces terminology drift without expanding the work into external/deep-link migration. If renamed destinations are desired, decide canonical names and alias behavior together before route tickets publish new links.

## Implementation evidence to request

Every route ticket should link its capability mapping and the shared owner/issues it depends on, including the existing primitive chosen when no shared change is needed. Record both where a moved control is found and what state it preserves. Include meaningful checks for the roles actually admitted by that route, relevant feature/access variants, light/dark, collapsed/expanded shell where used, phone/wide layouts, enlarged fonts/zoom, keyboard/focus and long translated data.

Use existing behavioral coverage as evidence to retain, not a substitute for runtime verification. Representative suites cover sidebar, table/mobile controls, overlay compatibility, TanStack field wiring, dashboard layout eligibility, refresh draft retention, calendar/timezone actions, manual/offline recovery and scheduling publish acknowledgment. Route tickets must run applicable checks and verify their real interactions. This discovery task did not run the application, mutate tenant data or require environment variables.
