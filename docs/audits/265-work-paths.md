### W23 — audit package verification (source-reachable)

`app/api/audit-export/verify/route.ts::POST` and
`SET/audit-export/actions.ts::verifyAuditPackageAction` →
`lib/audit-export/application/verification-service.ts::verifyPackage`.
Scope is O/package/authorized verifying U; the service loads the package with
both package ID and organization ID. Route CASL and settings organization-admin
checks are separate caller authorization boundaries.

The service reads stored file/Merkle/signature/timestamp proofs and calls storage,
signing and timestamp providers. For audit packs it downloads the package through
an organization-scoped presigned URL and checks required evidence files exist
(`verification-service.ts:386–439`). It then separately inserts
`auditVerificationLog` with package identity, checks and verifying actor
(`:453–486`). Provider work and that evidence write are not one work-graph snapshot
transaction or a completed-work replay receipt.

**#324/#306 acceptance:** exercise both entry points and the actual verification
owner when package representations change; preserve organization/package
authorization, verification history and linked cleanup. Explicitly distinguish
stored package proof/file-presence checks from employee-chain continuity,
original actor/capture truth and historical versus post-anchor assurance. A
package verification success cannot erase a disclosed lineage limitation or
certify payroll readiness. Test missing/misleading graph evidence and authorized
limitation reporting; retire unsupported verification claims rather than
relabeling file presence as semantic completeness.

## Shared persistence and reader obligations

Schema roots: `db/schema/time-tracking.ts`, `time-record.ts`,
`approval-workflow.ts` and relations. The work operation owns entries, append
position, closed inactive period, canonical base/detail, attribution/allocations,
approval participation, submitted/result evidence, graph revisions, receipt and
required follow-up intents in one actual transaction. Workflow execution retains
transition authority and its existing command receipts/outbox. The current
helper/transaction interfaces are prior art, not proof of that whole contract.

Readers to include when retention or graph representation changes:

- `TT/actions/queries.ts`, `TT/workday-timeline-data.ts`, calendar loaders and
  `lib/work-balance/service.ts`/`period-aggregation.ts`: exclude business-deleted
  work from payable/occupied interpretation while retaining append evidence.
- `lib/reports/generator.ts`, `lib/exports/processor.ts`, `lib/jobs/export-processor.ts`
  and audit-pack processing: disclose incomplete scope and preserve source fields;
  required assurance cannot be inferred from matching hashes or selected rows.
- Approval inbox/requester projections, domain adapters and compatibility readers:
  original approval participation is not current pending state; historical cycles
  remain distinct and cannot be reconstructed from current assignment or labels.

All repair/admin/cleanup entry points are also mutation participants; see R13–R16.
Source-only discovery of no extra caller is not effective retirement. #327 must
repeat caller/build/SQL inventory at the release revision and attach the
operational drain/disable evidence before all-writer claims.
