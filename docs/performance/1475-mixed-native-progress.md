# Mixed Native progress acknowledgments

This is a prospective observation method for the existing mixed operator. It has no actual mixed feasibility or numerical acceptance result. Historical captures remain unchanged.

`mixedNativeProgressPolicy`, exported by `control-cancellation-evidence.mjs`, identifies version 1, prefix `acknowledged-mixed-native-prefix-v1`, ledger `mixed-native-progress-observations-v1`, the existing 10,000ms observer ceiling, and `existing-mixed-stop-guards-only`. Every current mixed report must record this exact object as `nativeProgressPolicy`. Every one of its four contexts must carry a source/runtime/context-bound `mixedProgress` ledger, including guards with no Native candidate. Missing, copied, deleted or malformed evidence blocks derivation.

The normal collector's mixed-only `acknowledgeMixedProgress({ operationDeadlineMs })` and `confirmMixedProgress(token)` run at the existing setup, command-entry, reader-stop and pre-submit guards. Both reader stop callbacks are awaited. The live token belongs to its exact observer instance and cannot be copied or reused. Genuine errors and application UNKNOWNs stop before metadata acquisition and are checked again before work resumes. A new failed-request ID during the acknowledgment also stops. Canceled or unread current packets never qualify for acquisition.

For the narrow existing known-Extra/natural-EOF Native family, the request-local proof is recomputed. An independent prefix validator then requires actual public CDP execution-context unique ID, frame, loader and observed document-generation joins; the same document and controller across read-only registration/cookie/public-source reads; and actual open journal cuts. It does not reconstruct continuous controller history. Cookie operations have bounded, independently identified read-only ownership and completion records. Another acknowledgment's pending cookie read is allowed only when that exact read-only ownership partition is known; this acknowledgment must have completed. Unknown ownership, errors and pending own operations block.

The proxy observes headers before its existing `writeHead` call. Its mixed-only lifecycle records acceptance, upstream creation, received headers, the actual `writeHead` return and upstream close as technical ordinals. An open request remains open with no header-forward event; it is never converted to a closed zero. The writeHead fact describes the source call, not completed downstream delivery. No forwarding/body/header behavior changes.

Each prefix is immutable by value and replayed against the final context's source authority, principal operations, worker-event prefix and proxy lifecycle. Final browser, application, transport, all-five-metric and Native lifetime closure checks still run independently. A prefix cannot satisfy the closed Native validator. The body parser, cancellation families, raw failure counts, 20 pairs/40 commands, 100-read bound, workload, deadline positions and numerical policies 2/3/9 are unchanged.

At guards without an existing absolute operation deadline, the receipt explicitly records its absence and uses only the existing finite observer ceiling. Where an actual overlap deadline already exists, the observation uses its remaining minimum; it never renews the deadline. New metadata execution overhead is recorded and is not subtracted. Lost reader overlap stops instead of waiting/retrying to recover it. There are no new sleeps, drains, mutexes or business requests.

The existing 10,000-record and 32MiB retained-evidence bounds stay strict. The theoretical maximum number of guard invocations permitted by the 3-reader/40-command/100-read recipe can exceed 10,000; hitting that bound is an explicit feasibility failure. No higher guard cap or guessed compression is admitted. Source fingerprints and future BOTH-phase preparation must include the new observation method. Actual Root-owned mixed feasibility is still required.
