# Proposed web clock status transport

This is a review candidate. It has not been applied to either frozen comparison fixture or approved for a baseline rebuild.

The latest failed Original observation recorded an accepted clock-in while the mounted status query remained fetching and invalidated with cached OUT, one observer and no fetch failures. No post-write clock-status action reached the observed network boundary. The exact installed Next FIFO and real-hook regression reproduces a possible mechanism: an unrelated Dashboard action can hold a later status action behind it while the independent REST command succeeds. The actual queued invocation and reason for the pending Dashboard action remain unobserved.

The candidate changes only the web status transport. A private `GET /api/time-clock/status` invokes that build's existing `getTimeClockStatus` directly on the server. The shared client uses same-origin credentials and no-store fetch. It does not consume TanStack's AbortSignal, add polling, retry a write or change clock command routes. The existing query key, invalidation, stale time, enabled guards and all mutation callbacks remain unchanged.

Each phase's business reader and authorization code remain byte-for-byte unchanged. Original still uses its session, active organization and active employee lookup; HEAD still uses its existing authenticated context and membership/access checks. Missing reader context keeps the legacy empty OUT tuple as HTTP200. Unexpected reader or serialization failures produce a generic private no-store500, and the client treats non200, malformed JSON or invalid data as unavailable rather than successful OUT. Caller organization and employee parameters are not accepted. This deliberately does not reuse the desktop endpoint, whose actor admission, error statuses and smaller result differ.

The wire contract preserves employee/period identifiers, current task, open-break state and break zone. Only Date values cross the HTTP boundary as canonical UTC ISO instants and return as Date values for existing callers; no business date arithmetic or viewer timezone conversion changes. Strict schema checks retain nulls, validate task state and reject missing/extra/wrong fields or malformed instants. Error messages contain no input values.

Tests exercise the actual hook, real QueryClient, two consumers and the complete installed Next FIFO/callServer modules. The legacy transport remains blocked until only the Dashboard head is released; the new GET and actual route adapter in an inert HTTP boundary reaches IN while that same head remains pending. No-head controls remain positive. A naturally superseded prior GET is allowed to finish without a network AbortSignal and cannot overwrite the newer IN. Route tests prove one local reader call with no caller scope arguments, fresh result delegation, full task/break transport, generic errors and no-store headers. These transport tests mock the existing reader boundary; they do not claim database or authorization integration coverage. Exact reader/auth source invariance supplies the policy-parity evidence for independent review.

Applying identical transport changes to both comparison builds would still change the Original performance baseline by bypassing its action queue. The earlier advisory-read approval does not cover it. User approval, fresh builds and exact source qualification are required before applying either candidate; benchmark samples, deadlines, numeric policies, error gates and all earlier failed observations stay unchanged. Global action parallelism, Dashboard optimization and the desktop status API are outside this proposal.
