# Prospective browser failure evidence

Clean-evidence policy3 retains the raw browser `failedRequests` metric in both phases. Acceptance requires a complete request-ID partition into genuine failures, unknown failures and positively proved protocol controls. Genuine or unknown measured failures block capture and budget derivation. A canceled request is never recorded as a successful application payload.

The active proof requires actual browser-received Flight bytes, supported framing and required model dependencies, and the same decoded body hash from a unique naturally completed proxy response. HTTP errors, Flight error rows, explicit root action failures, incomplete bodies, ambiguous identity, pending observations and caps reject the proof. Cached native revalidation remains UNKNOWN: the earlier prototype omitted semantic Vary dimensions and a stable browser principal proof. Unsupported segment contracts remain UNKNOWN.

The source-qualified runtime-shell request (`RSC:1`, `Next-Router-Prefetch:3`, no segment subtype) has a narrower output claim. A marked partial response may postpone a lazy rendered child beneath a known React Suspense boundary with a fully fulfilled fallback. Required tree/Map/metadata/type/module references, other component props, plain or promise references, missing fallbacks and cyclic fallback output remain blocking. The same model reached through another required path is still required. This proves only the represented shell output, preserving partiality; it does not claim a complete route. Synthetic tests follow installed Next16.4 buffering and React partial-stream behavior. Real corpus validation remains pending.

The main navigation's declared `p` runtime-prefetch stream supports its source-produced `R`/Uint8Array or `r`/byte-stream framing. Exact byte lengths and explicit stream close are required. Its reassembled Flight has a separate required graph; nested errors and malformed data cannot disappear inside opaque outer bytes. A marked partial embedded prefetch may use the same qualified Suspense-output boundary rule, while the main navigation's references remain required. Decoded-byte, row and model-work budgets are shared across the outer and one permitted inner level. Other binary roles remain UNKNOWN. A complete marker never permits missing references.

A separate `embedded-partial-prefetch-representation` claim covers postponed lazy references in component props reached through the embedded `r` output graph. It requires the inner `~` marker and fulfilled root, tree, Map, component-type and eager metadata. Next stores this detached partial cache representation without rendering those props; the claim explicitly records `renderableOutputClaim: false`. It proves neither a renderable shell nor complete output for a later navigation. Missing plain or promise references, component types, required fallbacks, main-navigation data and complete-marker holes remain UNKNOWN. Nested framing and positive-error inspection still run over the whole bounded embedded stream.

On a known Suspense element with a fulfilled props object, an omitted `fallback` property is React's empty fallback, as are literal null and explicit undefined. `knownEmptyFallbacks` records those cases. An unresolved fallback reference remains UNKNOWN; resolving the props object never supplies a missing model row. An empty fallback also proves no visible application content, which remains subject to the ordinary readiness checks.

Within the partial embedded cache representation only, a fallback React-element tuple may name a fulfilled, structurally valid Flight `I` module record when all of its props and eager dependencies are fulfilled. `representedComponentFallbacks` records this representation, while `renderableOutputClaim` remains false: the observer never invokes that module or claims its rendered fallback is known. A bare module tuple, missing type or prop reference, complete-marker hole and protocol error still reject. The ordinary renderable RuntimeShell claim retains its stricter fallback rule.

Passive native-environment metadata separately records the actual executable/launch and collector-source hashes, the four public worker files under the app manifest's serving root, and bounded existing Puppeteer target-manager events for the actual isolated context. It adds no browser flags, discovery commands or application requests. Missing files/process/target facts and event overflow remain explicit. Controller observation and a public-file recheck are marked uncollected; this metadata makes no producer-certificate or native-control acceptance claim. The complete operator fingerprint map remains required independently of the two observed source-file hashes.

Core `protocolErrors` observations retain positively observed Flight errors and root action failures, including qualified embedded streams, even when HTTP completes without a CDP loading failure. Missing or nonzero observations reject both phases independently of the raw browser-failure partition. Known length-framed binary data is skipped correctly while scanning outer error records; arbitrary binary business data is not interpreted as nested Flight. Zero observed errors is not a claim that every optional unread body was semantically fulfilled.
