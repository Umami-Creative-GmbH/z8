# Requested documents enter the file at once; review decides the request, not the document

An officer can ask an employee for a certificate or other document with a **document request**, and an officer reviews what the employee submits. We decided that the employee's uploads become employee documents in the personnel file the moment they are uploaded, exactly like any employee upload, and that accepting or returning a submission decides only the request. A returned document stays in the file until an officer deletes it. Only acceptance changes anything else: the **renewed document** stops counting as expiring, and a renewed skill certificate's employee skill is linked to the new certificates, which moves its skill expiry date. Any officer whose current grant covers the employee and the category may decide a request; there is no named reviewer.

## Considered Options

- **Hold uploads outside the file until accepted.** Rejected: a second store of not-yet-accepted documents would need its own visibility, retention, purge and export next to the personnel file that already has them, and employee uploads would behave differently depending on whether a request asked for them.
- **A named reviewer per request.** Rejected: it needs a reassign action and handling for a reviewer who departs or loses their grant. Coverage is already checked live for every personnel file notification, so whoever covers the employee and category now is the reviewer.
- **The employee's upload renews the skill.** Rejected: a skill expiry date drives staffing, so only an officer may move it, as the skill certificate rules already require.

## Consequences

- A returned or cancelled request can leave documents in the file that nobody accepted. They are ordinary shared documents: the employee sees them, and retention and purge treat them like every other document.
- An officer who loses coverage loses sight of requests they made; the request stays with whoever covers it now.
